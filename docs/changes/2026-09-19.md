## Part 1 — Protein target calculator (EN+ZH)
## Context

Vincent reviewed four reference sites he'd been sent (freeaitool.com, makeronsite.com,
dashed-tech.com, beets3d.cn) after an earlier recommendation to pause posting. His question:
*"should I create more posts based on the top posts instead?"*

Diagnosis from live GSC (30d, 2026-08-20 → 2026-09-16):

```
traindecade    34 EN + 34 ZH   4 clicks   ~185 impr   pos 6–95
builderdecade  37 EN + 37 ZH   2 clicks   ~120 impr   pos 3–75
```

The reference sites' common factor is **not** post volume and **not** selling a product
(freeaitool.com sells nothing). It is a **terminal action** on every page — a next step a
reader can take. traindecade posts were closed loops: traffic → page → end. This ships the
first terminal action.

Spec: `vault: Projects/TrainDecade/Specs/Reader-Action-Layer.md`

## Changes

### 1. New `protein-calculator` shortcode (EN + ZH)
- `layouts/shortcodes/protein-calculator.html` — server-rendered, language-aware.
- `assets/js/protein-calculator.js` — vanilla JS, no CDN, no framework, no dependencies.
- CSS appended to `assets/css/extended/custom.css`, using existing theme vars so dark
  mode works automatically (no new `[data-theme]` override needed).

**Inputs:** bodyweight (kg/lb toggle) · goal (cut/maintain/build) · resistance training
(yes/no) · body-composition estimate (lean/average/higher).

**Outputs:** daily target in g/day, g per kg, per-meal split, and an explanatory note.
The note states *why* the number differs from the 1.6 g/kg rule of thumb when body fat is
elevated, rather than silently adjusting.

### 2. Email capture deliberately DROPPED
Vincent challenged the original spec: *"Is it too aggressive to get email now? What will I
do with the email at this stage?"* Correct call — there is nothing to send yet, and an
unused list goes cold. The PDF was dropped too (it existed only as the capture incentive,
and a thin PDF burns the one first impression).

**Acceptance criterion #11 enforces this: no email field, no form, no popup.** Verified in
the built output — `formCount: 0`, `hasEmailInput: false`. Do not add capture here without
a fresh decision; see the spec's "Out of scope" section.

Replacement measurement: GA4 event `calculator_used` with a `source_post` param, fired once
per session, giving attribution without any form.

### 3. Lean-mass basis aligned with the published post (Option B)
The calculator's body-composition input would otherwise produce a number that contradicts
the published 1.6 g/kg figure. Both language versions of
`how-much-protein-do-you-really-need` now carry a caveat paragraph explaining that 1.6 g/kg
is calculated on **total** bodyweight, that protein targets actually scale with **lean
mass**, and linking down to the calculator. The widget and the prose now agree.

## QA fixes (build-tester gate, 2026-09-19)

Build-tester reviewed pre-commit state and returned **⚠️ ship with warnings**, finding three
defects the builder missed. All three are fixed and re-verified:

**D1 — broken in-page anchor (real defect).** The caveat paragraphs deep-link to
`#protein-target-calculator`, but the raw `<div id="protein-target-calculator"></div>` in the
Markdown was **silently stripped by Goldmark's safe renderer** (the source of the
`WARN Raw HTML omitted while rendering` lines in the build). The link did nothing.
The builder's original check was a **false positive** — it grepped for the string and matched
the *link's href*, not the target element.
*Fix:* the id now lives on the heading (`## Run your own numbers {#protein-target-calculator}`),
which Goldmark renders natively. Deliberately **not** fixed by enabling
`markup.goldmark.renderer.unsafe` — that would trade a link bug for site-wide raw-HTML injection.
*Verified:* `document.getElementById('protein-target-calculator')` returns the `<h2>` in both
EN and ZH, and the deep-link scrolls the page.

**D2 — per-meal output contradicted the published band.** The post states the per-meal dose is
~25–40 g, but the widget capped at 45 g, so heavier users saw 44–45 g/meal.
*Fix:* cap lowered to 40 g, and the meal count now derives from the daily target
(`Math.max(3, Math.min(5, Math.ceil(target / perMeal)))`) with the displayed per-meal figure
bounded by the target, so the split can never imply a dose above the published band.
*Verified:* swept 9 weights × 3 goals × 3 body-fat options — maximum per-meal is exactly **40 g**.

**D3 — `min`/`max` were UI hints only.** Devtools/paste bypassed them, giving `0 g` or
`NaN g per kg`.
*Fix:* hard clamp in `currentKg()` — non-finite or ≤0 returns 0 (renders the em-dash
placeholder), otherwise clamped to 30–300 kg.
*Verified:* 0.5 → clamped, 1e21 → clamped, negative/zero → placeholder, no NaN/Infinity in
the per-kg line.

**Re-test after fixes:** `hugo --gc --minify --cleanDestinationDir` exit 0 (the raw-HTML
warnings are now gone); `tests/test_multilingual.py` ✅; the maths matrix, unit-toggle, and
QA-fix suites all pass; both language pages re-checked live in a browser.

## Impact

Every page carrying this widget now ends in an action instead of a dead stop. Rollout is
**staggered on purpose**: this ships embedded on the protein post only. The spec's plan is

## Part 2 — Site-wide literal emphasis markers + regression guard
## Context

While fixing a small stray-asterisk typo in the ZH protein post (reported in the previous
changelog), a rendered-output audit revealed the problem was **site-wide, not a typo**:

```
308 stray asterisks visible to readers, across 19 ZH pages + 1 EN page
worst: collagen ZH (58), body-recomposition ZH (50), protein-comparison ZH (48)
```

Readers were literally seeing `**` and `*` in the prose across most of the Chinese site.

## Root cause (proven, not inferred)

Minimal goldmark tests isolated two independent failure modes in Hugo 0.165.0:

```
BROKEN  **重點：**      closing ** immediately preceded by CJK punctuation (：。？！，、；)
BROKEN  **重點。**
BROKEN  **如何？**
BROKEN  **a *[x](/y/)*。**   nested single-* run inside a ** span
BROKEN  中文**粗體**中文      opening ** preceded by a CJK character cannot OPEN
OK      **粗體**  ·  latin **bold text**  ·  **粗體**緊貼文字
```

CommonMark's emphasis-flanking rules require whitespace/word boundaries that CJK
text does not provide. The markers then fail to pair and leak as literal characters.
EN prose is largely unaffected — English requires a space before a closing marker anyway.

Compounding it, several files carried **genuinely unbalanced markers** (an odd number of
`**` on a line), which are plain authoring errors.

## Changes

### 1. `tests/check_no_stray_emphasis.py` — new regression guard
Strips `<script>`/`<style>` bodies (not just tags — JSON-LD escapes otherwise pollute the
count), extracts reader-visible text from every rendered post, and fails if any `*` or `__`
survives. Verified to **fail on the broken state** (exit 1, 308 strays) before the fix, and
to pass after — a guard that cannot fail is worthless, so this was checked both ways.

### 2. Wired into CI
`.github/workflows/hugo.yaml` — new step `Verify no stray emphasis markers` runs between
the existing multilingual check and the artifact upload, so this can never silently regress.

### 3. Content fixes across 37 files
- CJK-adjacent `**bold**` and `*italic*` markers removed (the text is preserved; CJK prose
  carries emphasis through sentence structure, and plain text is strictly better than
  markers readers can see).
- English-marked spans surrounded by ASCII left **untouched** — they render correctly.
- Three genuinely unbalanced markers repaired by hand:
  - `collagen-for-tendons-after-40` (EN) — moved the opening `**` before the author name.
  - `exercise-snacking-...` (EN) — removed an extra trailing `*`.
  - `somatic-awareness-body-feel` (EN) — fixed a `***` triple marker.

**Deliberately NOT done:** enabling `markup.goldmark.renderer.unsafe` to preserve bold via
raw `<strong>`. That would trade a marker bug for site-wide raw-HTML injection — the same
reasoning applied to the anchor fix in the previous changelog.

## Verification

| Check | Result |
|---|---|
| `hugo --gc --minify --cleanDestinationDir` | exit 0 |
| `tests/check_no_stray_emphasis.py` | ✅ 0 strays across 68 rendered posts (was 308) |
| `tests/test_multilingual.py` | ✅ 34 EN / 34 ZH paired, hreflang OK |
| Post counts | 34 EN / 34 ZH — unchanged |
| **Prose integrity** | ✅ 37 files diffed old-vs-new rendered text with all asterisks stripped: **0 files with non-asterisk text changes** |

The integrity check is the important one: it proves the fixer removed **markers only** and
did not damage a single word of prose. It built the pre-fix revision into a temp git
worktree and compared visible text character-by-character.

## Rollback

`1981db8` — wip commit captured immediately before the final content pass.

## Impact

Chinese readers can now read the site without seeing raw markdown syntax. This was invisible
to every existing check because no test looked at rendered *visible text* — the multilingual
suite only asserts EN/ZH pairing and language isolation. The new guard closes that gap for
this failure class.

## Note on methodology

The first two fixer attempts over-reached badly — one proposed **960** edits, another **671**
— because they pattern-matched on source heuristics and would have stripped legitimate
English italics. Both were caught in dry-run and discarded. The working fixer was driven by
**rendered-output ground truth**, not source regex. Worth remembering: for content defects,
verify against the built artifact, never against the source alone.
