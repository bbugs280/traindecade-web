# 2026-11-23 — Deploy pipeline repaired + GA4 event binding fixed

## Two defects found, both silent

### 1. 🔴 The deploy pipeline was disconnected — every push since 11 Nov was invisible

`traindecade.com` is served by **Cloudflare Pages**, but the GitHub Actions
workflow `.github/workflows/hugo.yaml` deploys to **GitHub Pages**. The two are
unrelated targets.

```
git push → GitHub Actions ✅ green → GitHub Pages (nobody visits)
                                  ✗  NO PATH TO traindecade.com
Cloudflare Pages project "traindecade" → Git Provider: "No"
                                        → manual upload only
```

**How it was found:** the repo built correctly (local `hugo` rendered
`gaincut-cta` twice on the target page), the CI run went green, and the live
page still had zero occurrences. `wrangler pages project list` showed
`Git Provider: No`.

**Blast radius:** every content change pushed between **2026-11-11 and
2026-11-23** never reached production. The 2026-11-22 GainCut connector on
45/45 ZH posts had never been live at any point before this session.

**Fix (this commit):** built locally and deployed with
`npx wrangler pages deploy ./public-deploy --project-name traindecade`.

⚠️ **This is still a manual step and will rot again.** The durable fix is to
connect the Cloudflare Pages project to the GitHub repo (Git provider =
GitHub) and delete or repoint the GitHub Pages workflow. Not done — needs a
decision on whether Cloudflare Pages builds Hugo itself or accepts the
Actions artefact.

### 2. 🔴 `gaincut_click` could never fire — the attribute was decorative

`layouts/partials/gaincut_cta.html` shipped:

```html
<a href="…utm_campaign=zh-{{ $slug }}"
   data-ga="gaincut_click"
   data-ga-location="zh-post-{{ $slug }}">
```

with a comment asserting *"data-ga is bound by the site's existing
outbound-click listener."*

That was **false**. `extend_footer.html` only ever emitted `outbound_click`; it
had **zero** references to `data-ga`. The event name existed only as an HTML
attribute nothing read.

**Consequence:** the card's checklist item *"verify the GA4 event actually
FIRES"* was unsatisfiable by construction. Any future check that looked for the
attribute in the HTML would have passed while the event stayed at zero forever.

**Fix:** the listener now reads `data-ga` and dispatches a second event with
`link_url`, `link_domain`, `link_text`, `location`, `page_path`,
`page_language`. `outbound_click` is retained (it is the wider net);
`gaincut_click` is the per-product signal.

## Test added — `tests/test_ga_event_binding.py`

Asserts on **rendered output**, not source, and — critically — asserts that the
**listener source reads the attribute**. An attribute in the HTML proves
nothing about what the Javascript does with it; that conflation is exactly what
let defect #2 ship.

```
9 checks: listener reads attribute · gtag dispatch exists ·
          CTA carries attribute · 45/45 ZH posts wired · 0 EN posts
```

Proven RED→GREEN: with the binding removed from a copy of the partial the test
fails with 2 problems; restored, it passes 45/45.
